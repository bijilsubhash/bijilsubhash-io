State-aware ingestion, or why your backfill keeps lying to you

2026-03-08·11 min read
dlt ingestion bigquery

Every incremental pipeline carries a small piece of mutable state: the cursor that says where the last run stopped. Most of the failures I get called into are not failures of the extract or the load. They are failures of that cursor — a value written before the load committed, a timezone that shifted under a filter, a source that backdates records after you have already moved past them.

The fix is rarely more compute. It is making the state explicit, versioned, and inspectable, so a backfill is a decision rather than a gamble. This post walks through how dlt models incremental state, where it breaks, and what to put around it.

Where the cursor comes from

A cursor is a promise about ordering. If the source cannot honour that promise, no amount of retry logic will save the load. Start by asking what guarantee the API actually gives you.

pipelines/orders.py 
@dlt.resource(write_disposition="merge", primary_key="id")
def orders(
    updated_at=dlt.sources.incremental(
        "updated_at",
        initial_value=pendulum.datetime(2024, 1, 1, tz="UTC"),
        lag_seconds=900,   # absorb late arrivals
    ),
):
    yield from client.paginate("/orders", since=updated_at.last_value)
note

A lag window is not a correctness fix. It buys time for late writes and nothing more.

tip

Persist the cursor after the load commits, never before. Wrap both in the same transaction boundary where the destination allows it.

warning

Deleting pipeline state to “force a full refresh” also discards the audit trail of what was loaded when. Version it instead.

The shape of a safe backfill

Treat the backfill as a separate, parameterised run that writes to the same tables through the same merge logic, with its own window and its own state key.

A pipeline you cannot re-run confidently is not a pipeline. It is an outage with a schedule.

— a colleague, during an incident review

A checklist before you re-run

  • Confirm the merge key is genuinely unique at the grain you load.1
  • Snapshot the current state value somewhere you can read later.
  • Bound the window. An unbounded backfill is a full refresh with extra steps.2
dlt ingestion bigquery

footnotes

  1. Composite keys are fine. Keys that are unique “in practice” are not. ↩
  2. Bounded windows also make cost predictable, which is how you get permission to run it. ↩

About

I am a data engineer in Sydney. I spend most of my time embedded with teams, building the platforms that turn their raw operational data into something they can actually make decisions with.

I did not start here. I finished a PhD in chemical engineering at UNSW in 2023, and for a while I assumed that was the career. What kept pulling my attention was the data underneath the research — the pipelines, the modelling, the tooling. So I moved into data science, then into data engineering, which is where the work has felt most like engineering: systems that have to keep running when nobody is watching them.

Since then I have worked across enterprise migrations, Series A startups building their first platform, and consulting engagements where the brief arrives half-formed. I founded NimbleStax in 2023 to do that work directly, and I teach Snowflake, dbt and AI engineering to enterprise cohorts through Breakout Labs.

Most of what I have learned came from maintaining things I built badly the first time. That is what this site is for. I write long posts about the modern data stack — dbt, dlt, Dagster, BigQuery, the architecture decisions around them — because the interesting part is never the tool, it is the tradeoff you accepted to use it.
